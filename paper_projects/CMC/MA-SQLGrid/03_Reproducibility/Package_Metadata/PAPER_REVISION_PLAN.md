## 1. 文档目的与总体判断

本文档依据最新版 LaTeX 及重新核验的逐题证据，给出面向 *Applied Sciences* 投稿的后续修改路线。目标不是简单增加篇幅或堆叠实验，而是解决当前版本中“论文主张与证据不完全对齐”的问题，使审稿人能够直接判断：五角色架构是否有效、其收益是否超出候选数量和模型调用预算带来的自然提升、验证式选择是否不依赖候选排列顺序，以及方法是否确实适用于电网数据库。

最新版 LaTeX 已经具备三项可靠基础：可审计的角色接口与追加式黑板、严格的只读执行和 gold 隔离机制，以及对非显著结果和回顾性分析边界的诚实报告。重新核验没有发现能够推翻80/100/101或主要统计表的单点数值错误。当前主要风险是以下四项证据与发布缺口：

1. 五角色架构没有通过预算匹配的端到端对照和角色消融得到直接验证；
2. 主要电网数据规模较小且为合成数据，无法支撑真实电网场景的外部有效性；
3. 历史候选池结果受到重复 SQL、最高分并列和固定来源顺序的明显影响；
4. 论文、公开仓库、数据可用性说明、PDF 和发布校验清单尚未形成同一版本的复现闭环。

因此，不建议仅重建 PDF 后直接投稿。推荐采用“完整增强路线”：先完成无需新增模型调用的选择器重分析和复现修复，再开展前瞻性端到端实验与电网外部验证，最后依据新证据更新论文。若时间、数据权利或计算资源不足，则应采用“保守收缩路线”，将论文定位为“可审计的多角色协调与评测协议”。

## 3. 文本部分的修改意见

### 3.1 标题、摘要与关键词

#### 需要修改什么

当前摘要已经明确五角色中包含确定性组件，把 `robust` 限定为 mutation denial、bounded execution 和 fail-closed evidence handling，并明确不建立五角色端到端准确率优势。这些表述是本轮评审确认的优点，应保留。

剩余任务取决于实验路线。若完成第4节所列的前瞻性端到端实验和电网外部验证，可以保留当前标题，并在摘要中加入预算匹配主结果、弃权/风险和成本。若没有完成这些实验，则当前 `Robust and Auditable Multi-Agent Framework` 仍强于实证证据，建议采用更保守的标题。

若无法完成上述实验，建议将标题调整为更保守的表述，例如：

> **MA-SQLGrid: An Auditable Multi-Role Coordination and Evaluation Framework for Power-Grid Text-to-SQL**

当前摘要的“应用问题—框架—实验设计—主要结果—证据边界”结构已经基本合格，无需无目的地整体重写。需要调整的是结果优先级：不要继续把历史池的80/180→100/180→101/180作为最接近“框架性能”的数字；若完成E1，应以E1的前瞻性主结果替换；若未完成，应继续明确写成 retrospective candidate-pool analysis，并把高并列和顺序敏感性与80/100/101放在同一结果句中。

#### 为什么要这样修改

当前标题容易使读者预期论文已经证明完整多智能体系统在电网 Text-to-SQL 上更准确、更鲁棒，但当前实验证据主要支持审计接口、验证流程和有限语料上的选择行为。标题和摘要必须与最强证据保持同一层级，否则即使正文限制写得谨慎，审稿人仍会认为中心主张被包装得过强。

#### 验收标准

- 摘要中的每个定量结论都能对应到正文的一张表或一幅图；
- 不再把非显著结果描述为“无影响”或“等效”；
- “robust”“multi-agent”“power-grid”均有可操作定义或明确适用边界；
- 摘要同时报告准确率、风险/安全性和成本，不只报告最佳准确率。

### 3.2 Introduction

#### 需要修改什么

当前引言已经把研究缺口定位为安全敏感数据库中的可追踪决策链、单快照执行与语义正确的区别，以及生成—验证—裁决证据的统一审计协议。这一逻辑无需重新搭建，应作为后续修改的固定主线。

贡献列表可以进一步明确为“设计贡献、实证贡献、资源贡献”三类，并为每条贡献标注证据边界：

1. **设计贡献：** 五类角色接口、追加式黑板、只读执行、gold 隔离和确定性裁决；
2. **实证贡献：** 在指定模型、数据库和预算条件下，对提示、值信息、候选选择、变形证据和顺序敏感性的系统测量；
3. **资源贡献：** 可复核的轨迹、配置、统计脚本、失败样例和版本化复现包。

若开展新实验，应增加两个研究问题：完整架构在相同模型调用和 token 预算下是否优于单智能体/单阶段流程；该结论是否能够迁移到未见电网模式。原有研究问题则应按“生成因素—组件作用—状态证据—候选选择”重新排列，使其与结果章节顺序一致。

#### 为什么要这样修改

当前引言已经主动披露没有五角色因果效应，这是正确处理。仍需解决的是：披露证据不足并不会自动证明框架有效；若不补E1，就必须把贡献稳定定位为审计协议与系统接口，而不是性能方法。

#### 验收标准

- 每条贡献均能在 Methods、Results 和 Discussion 中找到对应证据；
- 新增研究问题与新增实验一一对应；
- 删除无法被当前结果支撑的“general”“reliable”“robust across databases”等宽泛表达；
- 引言末尾明确论文不主张 SOTA，除非新增实验确实与同预算强基线完成了公平比较。

### 3.3 Related Work

#### 需要修改什么

当前稿件已经增加表1，但该表主要比较RGISQL、零样本提示、schema retrieval和DKA-SQL，没有覆盖正文中已经引用、且与本文最接近的TEAM、MAC-SQL、QC-MaSQL和R3。应扩充现有表1，而不是再创建一张内容重复的新表。对比维度至少包括：

- 是否显式分离分析、schema grounding、生成、验证与裁决；
- 是否使用只读或沙箱化执行；
- 是否检查多个数据库状态；
- 是否支持弃权；
- 是否保留机器可读审计轨迹；
- 是否执行 gold 隔离；
- 是否提供失败候选与完整复现材料；
- 推理成本和模型调用数是否报告。

正文不应只说“与已有方法不同”，而应说明 MA-SQLGrid 的最小新颖单元是什么。例如，创新点可以定位为“把候选来源、执行安全、多状态证据、确定性裁决和 gold 隔离统一到一个可回放协议”，而不是笼统声称首次使用多智能体解决 Text-to-SQL。

同时补齐当前 TeX 中两处 TODO 引用：test-suite/多状态评测相关论断，以及 grouped randomization、bootstrap、Holm 校正的统计依据。新增文献必须实际支持对应句子，不能只因主题相近而引用。

#### 为什么要这样修改

本文的方法新颖性主要是系统与协议层面的组合创新，因此需要用明确的功能维度与最接近工作比较。缺少这种比较时，审稿人容易把框架视为已有 staged pipeline 的重新命名。

#### 验收标准

- 对比表中的每个判断均可由被引论文或其公开实现核验；
- 正文明确区分“已有单项技术”和“本文统一协议的新增部分”；
- 清除所有 TODO 和未被文献支持的首次性主张；
- 相关工作不使用数学推导数量作为创新性判断标准。

### 3.4 Materials and Methods

#### 需要修改什么

当前方法章节已经较清楚地披露生成实验没有多智能体协商、历史池没有新LLM调用、gold在黑板密封后加载。剩余问题是把以下三个层级在小节标题、流程图和术语上彻底分开：

1. **框架规范：** 五角色接口、消息类型、黑板状态、执行器安全策略和裁决规则；
2. **前瞻性系统实例：** 哪些角色实际调用模型、每题调用几次、提示和 schema 如何传递、候选如何规范化与去重；
3. **历史候选池分析：** 候选来自何处、为何没有新模型调用、规则在何时冻结、哪些结果在规则开发时已经可见。

通用 SQL Synthesizer 和Algorithm 1声明执行 exact-duplicate removal，但主要历史实验通过 `Frozen Candidate Provider` 固定保留八个来源槽位。修订稿必须明确写出：历史实验为了来源审计而有意绕过了通用去重路径，因此它是slot-level retrospective study，而不是通用五角色算法的标准运行。建议把“唯一 SQL 候选”作为新的裁决单元，把多个模型/提示来源作为该候选的 provenance 列表；若继续保留全部八槽，也要分别报告slot-level和unique-SQL-level结果。

新增实验的方法应在运行前写入协议并冻结，至少记录：数据版本、问题 split、模型和量化版本、解码参数、提示模板哈希、最大调用次数、token 上限、超时、执行器版本、候选去重规则、并列规则、弃权规则、主指标、主要对比和多重检验族。禁止在看到新测试集 gold 后继续修改选择权重或 tie-break。

数据部分应增加问题类型分布、schema 规模、SQL 结构复杂度、模板或来源簇、开发/测试隔离过程，以及专家审核流程。对于当前 GridDB，应明确说明8表98行的规模、评测问题在开发期间的可见性，以及它不是前瞻性盲测。

#### 为什么要这样修改

虽然当前稿件已经多次说明各实验不能合并为一个框架准确率，但通用算法的去重规则与主要历史研究的八槽规则仍不同。方法层级分离可以消除“主要历史结果就是标准五角色算法输出”的误读，也能让后续实验真正检验架构而不是来源槽位构成。

#### 验收标准

- 读者可以从 Methods 单独复原每个实验的实际数据流和模型调用数；
- 候选“槽位”“唯一 SQL”“执行结果等价类”和“来源”四个概念被严格区分；
- 所有主分析的规则都有预先冻结的配置或清单；
- 数据可见性、规则开发边界和结果暴露情况被完整披露。

### 3.5 Results

#### 需要修改什么

结果章节应按证据强度而不是项目执行历史重新组织：

1. 前瞻性端到端对照；
2. 角色和验证组件消融；
3. 未见电网模式与 BIRD 的外部验证；
4. 候选去重、顺序随机化和弃权分析；
5. 提示因素与构造状态等诊断性实验；
6. 工程安全与复现检查。

每项主要结果至少同时报告：分子/分母、绝对差值、相对差值、效应量区间、校正后显著性、模型调用数、token 或延迟。若 primary contrast 未达到预先定义的标准，应直接报告未得到支持，不要转而突出某个未经预注册的子组。

历史池结果应把“默认固定顺序”“反向顺序”“多次随机顺序”“去重后随机并列”“开发集选择的最佳单来源”和“oracle”放在同一张主表中。80→101 只能作为默认历史配置的一列，不能继续承担完整框架有效性的主证据。新增失败分析应至少区分：schema 错误、join 错误、聚合/分组错误、排序或限制错误、值错误、可执行但语义错误、安全拒绝、验证器误伤和并列退化。

#### 为什么要这样修改

当前结果完整但证据层级分散。重新组织后，审稿人首先看到真正回答中心研究问题的结果，再看到解释性诊断，能够避免用回顾性描述代替方法验证。

#### 验收标准

- 每个研究问题都有一个明确的主表或主图；
- 主要对比与探索性分析在表注和正文中明确区分；
- 所有“improve”“outperform”“robust”等动词都由相应统计和预算对照支持；
- 负结果、harm cases 和验证器误伤不被移入补充材料以弱化其重要性。

### 3.6 Discussion、Limitations and Future Work

#### 需要修改什么

当前Discussion已经围绕“证据说明了什么、没有说明什么”展开，并正确讨论了验证器不能保证语义正确、低分辨率评分产生大量并列以及来源顺序进入tie-break。这部分不需要重写，只需用E3的唯一SQL级结果替换纯槽位级解释，并在新增实验后更新机制判断。

当前稿件已经明确区分admissible、executable和semantically correct，也已经将全部构造状态非显著结果解释为有限诊断证据。这些边界必须保留；不要在后续压缩篇幅时删除。

Limitations已覆盖合成GridDB、开发可见性、BIRD非电网、历史池结果暴露、语义有效性和排序稳定性。建议仅补充两点：历史八槽研究与通用去重架构的候选单位差异；公开数据/许可边界尚未形成一致release。若不开展E2，还应明确“power-grid”只指受控案例，而非部署范围。

#### 为什么要这样修改

这些限制本身不会导致拒稿，真正危险的是让读者自行发现它们却无法确认作者是否理解其影响。主动给出机制边界能够将“缺陷”转化为清晰的适用范围，并强化论文严谨、可审计的定位。

#### 验收标准

- Discussion 不把统计非显著解释为等效或稳定；
- 清楚解释验证器为什么会 rescue，也会 harm；
- Limitations 中每个结构性限制都对应一个不能推广的具体结论；
- Future Work 不再替代当前核心主张所需的验证。

### 3.7 Conclusion

#### 需要修改什么

当前结论已经较准确地区分了“架构规范”“回顾性候选选择证据”和“尚未验证的端到端因果收益”，这一收缩应当保留。后续修改取决于实验路线：若E1/E2表明五角色系统在同预算和未见电网模式上稳定优于强基线，结论才可增加完整系统的性能主张，并同时报告成本与适用范围；若未补齐，则继续以审计协议、失败保留、只读安全和条件性诊断为中心，不得把回顾性八槽结果改写成完整架构带来的准确率提升。

#### 为什么要这样修改

结论是编辑和审稿人判断是否过度宣传的重点位置。它必须是证据的压缩，而不是愿景的扩写。

#### 验收标准

- 结论中的所有定量数字均来自预先定义的主要分析；
- 不引用 oracle 结果作为可部署性能；
- 不将合成案例推广为真实电网部署；
- 明确说明框架的主要价值究竟是准确率、风险控制、审计能力，还是三者中的特定组合。

### 3.8 Reproducibility、Data Availability 与投稿材料

#### 需要修改什么

公开仓库必须更新为与投稿稿件完全一致的版本，并使用 release tag、commit hash 或 DOI 固定。当前公开仓库仍对应旧的 C1--C5/x10 实验，并记录 `gpt-5.4-mini` 与 `deepseek-chat`；它不能支持最新版 LaTeX 中的 Qwen/Granite、五角色协议、BIRD、构造状态和历史候选池结果。仓库应至少包含环境锁定、数据构建或取得说明、split、提示模板、运行配置、原始预测、候选池、统计脚本、失败轨迹和一键验证入口。不能只提供聚合表而无法追溯到逐题结果。

对于不能公开的 GridDB 和问题语料，应在 Data Availability 中说明具体权利限制、权利确认主体和可获得方式；若数据完全由作者构建，应尽快完成权利确认并公开生成器、schema、数据和 gold。当前公开仓库称相关原始数据和产物采用 CC BY 4.0，而本地最新版 data card 又称 GridDB 再分发许可尚未解决，这两种表述不能同时保留。应由作者或数据权利人确认后形成一份唯一、可执行的许可说明，并同步修改论文、data card、仓库 LICENSE/README 与 release。第三方 BIRD 数据可以不重复分发，但应记录官方下载位置、版本和校验值。

投稿前还需完成以下机械修复：填写并经作者确认通讯邮箱；确认作者顺序、单位、基金编号、CRediT、利益冲突和数据声明；补齐 TeX 中测试套件/多状态方法以及 grouped randomization/bootstrap/Holm correction 的引用 TODO；重新构建 PDF；更新 `FILE_SHA256SUMS.txt`、`RELEASE_MANIFEST.json` 和发布日期；运行 `verify_package.py`、全部单元测试和视觉 QA；确认公开仓库 README 中的题目、模型、实验条件和主要数字与论文一致。当前直接执行 `verify_package.py` 会因 `02_LaTeX/paper_applsci.tex` 哈希不匹配而失败；虽然图表计数、数据行数和框架/执行器单元测试可以通过，但这只能证明局部内容可读，不能证明投稿 release 已一致。

#### 为什么要这样修改

论文把 auditable 和 reproducible 作为主要价值，因此复现包的不一致会比普通论文受到更严重的负面评价。该问题不影响方法本身，却可能直接导致审稿人无法核验或编辑要求补件。

#### 验收标准

- 从干净环境按照 README 可以重建论文主表，或对无法重建部分给出准确、可验证的边界说明；
- 论文、PDF、仓库、manifest 和哈希对应同一版本；
- 逐题数据能够追踪到图表中的聚合数字；
- 论文、data card、仓库与许可证对 GridDB 的再分发权利给出一致说明；
- 投稿包中不存在占位邮箱、TODO、旧标题或旧实验配置。

## 4. 实验部分的补充方案

### 4.1 实验 E1：预算匹配的端到端架构对照

**优先级：P1；需要新增模型调用。**

#### 研究目的

直接回答完整五角色系统是否在相同候选预算、模型预算和测试问题上优于强单智能体或较简单的模块化流程。该实验是保留当前“multi-agent framework”中心定位的必要条件。

#### 数据与冻结要求

- 使用规则冻结后才首次揭示 gold 的前瞻性测试集；当前180题不应继续作为唯一主测试集，因为规则开发已经接触过同一批问题及结果。
- 先固定数据、模型、提示、候选数、执行器和统计方案，再运行正式测试。
- 样本量应依据预期最小有意义差异和簇内相关性进行功效分析；操作上建议覆盖至少3个不同 schema、约300题以上，但最终数量应由功效分析而不是方便性决定。
- 至少使用两个能力不同的 backbone，以判断结论是否只适用于单一模型。

#### 建议对照组

| 条件 | 说明 | 要隔离的因素 |
|---|---|---|
| A0 Direct | 单次直接生成，使用完整 schema | 最低成本基线 |
| A1 Direct + self-check | 同一模型生成后自检/修订，调用预算与完整系统对齐 | 多次调用是否已足以解释收益 |
| A2 Same-candidate ensemble | 生成与完整系统相同数量的候选，但使用简单固定或多数规则选择 | 候选数量收益 |
| A3 Validation-only | 使用相同候选，加只读安全和执行验证，不使用多状态 critic | 基础验证收益 |
| A4 Full MA-SQLGrid | 完整角色接口、黑板、验证、critic、裁决和弃权 | 完整系统效果 |
| A5 Full minus one role | 分别移除 Query Analyst、Schema Cartographer 或 critic；候选和预算保持一致 | 关键角色消融 |

不能让 A4 因拥有更多候选或更多 token 而天然占优。若无法做到完全相同调用数，应同时提供两种比较：equal-call/equal-token 对照，以及 fixed-system-configuration 的实际成本对照。

#### 主要指标

- 结果集等价准确率或严格定义的 execution accuracy；
- 安全违规率、不可执行率和 validator false-accept；
- 弃权率、coverage、selective risk 和 risk–coverage 曲线；
- rescue/harm 数量及其错误类型；
- 平均和 P95 延迟、模型调用数、输入/输出 token；
- 审计轨迹完整率与可回放率。

#### 统计方案

提前指定 A4 对 A1、A4 对 A2、A4 对 A3 为主要对比，并对这一检验族进行多重校正。题目级结果采用配对检验；存在模板或生成来源时使用预先定义的结构簇进行随机化或 bootstrap；跨数据库实验应把 database 作为独立性层级之一。除 p 值外，必须报告绝对差值和区间。

#### 成功与失败如何解释

- 若 A4 在同预算下提高正确率或降低 selective risk，且结果跨 backbone/数据库方向一致，可保留方法性能主张；
- 若 A4 只比 A0 好、但不优于 A1/A2，则收益主要来自额外调用或候选数量，论文应把贡献定位到审计与风险控制；
- 若 critic 不改善准确率但显著减少错误接受，可将其定位为安全组件；
- 若所有条件差异都不稳定，不应隐藏结果，应采用保守收缩路线。

#### 预期新增产出

- 主文表：端到端准确率、安全、弃权和成本对照；
- 主文图：risk–coverage 曲线；
- 补充表：逐角色消融、逐 backbone 和逐数据库结果；
- 逐题预测、轨迹、配置冻结文件和统计脚本。

### 4.2 实验 E2：未见电网模式的外部有效性验证

**优先级：P1；需要新增数据准备、专家审核和模型调用。**

#### 研究目的

验证论文的“power-grid”定位是否超出单个小型合成 GridDB。BIRD 只能证明一般数据库迁移，不能替代电网领域验证。

#### 数据设计

优先选择许可清晰、可重建的电网数据或模型，例如从 RTS、SimBench 或作者可公开的真实/半合成运维 schema 构建关系数据库。应至少包含两个与当前 GridDB 在表名、关系结构、设备编码和数据分布上明显不同的 schema；理想情况下覆盖3个以上数据库。

问题集应覆盖以下类别：设备状态查询、拓扑与多跳关系、时间窗口聚合、告警/故障事件、缺失遥测、单位与阈值、排序/Top-k、分组统计以及跨资产类型比较。开发集与正式测试集必须按数据库或问题族隔离，不能仅随机拆分同一模板的实例。

#### 专家审核

- 由两名独立的电网或电力信息系统专家审核问题自然性、schema 可回答性、gold SQL 和允许的等价结果；
- 记录独立审核、一致率、分歧类型和第三方裁决；
- 在正式模型运行前冻结问题、gold、数据库版本和评测脚本；
- 对构造或模板扩增的问题明确标注来源，避免把同一模板的表面改写当成独立样本。

#### 主要分析

报告总体结果以及按数据库、查询类型、join 深度和 SQL 复杂度分层的结果。重点观察跨 schema 后的错误类型变化，以及 Schema Cartographer 是否真正减少 schema linking 和 join 错误。E1 的主要系统对照应在该数据上复用，而不是另设不一致的实验流程。

#### 成功与失败如何解释

- 若效果在多个未见电网 schema 上方向一致，可将结论扩展到“tested power-grid schemas”；
- 若只在原 GridDB 有效，应将论文定位为单案例工程研究，并把跨模式适用性列为未验证；
- 若专家审核发现大量问题不自然或 gold 不唯一，应先修数据，不得用模型结果掩盖数据有效性问题。

#### 预期新增产出

- 数据集/data card、schema 图、问题分类和专家审核记录；
- 主文表：跨电网数据库结果；
- 主文图：按问题类型的误差分布；
- 补充材料：全部问题、gold、等价规则和数据构建脚本。

### 4.3 实验 E3：候选去重、并列和顺序稳健性重分析

**优先级：P1；现有数据可以完成，不需要新增 LLM 调用。**

#### 研究目的

判断历史池的20–21题增益究竟来自验证证据，还是主要来自固定槽位顺序、模型来源先验和重复 SQL。该实验应在任何新模型运行之前完成，因为它会决定论文是否还能把历史池结果作为主要证据。

当前诊断已经显示该问题不是理论上的担忧：180题中有130题出现槽位级最高分并列，平均最高分槽位数为5.40；默认 tie-break 使178/180次选择落到 Qwen 来源；反转候选顺序后 validation/full 结果由100/101变为117/118。对密封黑板的逐题检查还发现，156/180个候选池包含规范化后完全相同的 SQL，113/180题的槽位级最高分集合内部存在重复 SQL。与此同时，按唯一 SQL 去重后仍有122/180题包含多个最高分唯一候选，平均最高分唯一 SQL 数为3.14，平均每池唯一 SQL 数为5.31。这说明“评分分辨率不足”仍是真实瓶颈，但原稿中的5.40和来源偏好是槽位级现象，不能直接解释为5.40个独立语义候选之间的并列。新分析必须回答“去重并消除顺序先验后，验证证据还剩多少独立增益”。

#### 必做分析

1. 使用明确的 SQL 规范化规则进行 exact-SQL 去重；如条件允许，再补充 AST 等价和执行结果等价视图；
2. 将重复 SQL 的多个来源保留为 provenance，但每个唯一候选只参与一次裁决；
3. 在每题最高分集合中进行大量随机并列选择，报告期望准确率和区间；
4. 对候选顺序进行大量随机置换，报告选择结果的均值、方差、最差值和最好值；
5. 保留原顺序与反向顺序作为可解释的端点，而不是唯一敏感性检查；
6. 比较固定首槽、仅使用开发集选择的最佳单来源、随机来源、简单多数、按执行结果共识、validation-only、full coordination 和 oracle；
7. 分别报告 slot-level 与 unique-SQL-level 的并列率、平均候选数、来源比例和准确率；
8. 重新计算 rescue、harm，并检查收益是否集中在某一模型或提示单元。

随机化次数应足以使 Monte Carlo 误差远小于报告的效应；建议至少10,000次，并固定随机种子和公开代码。主要结论应基于顺序边际化后的估计，而不是任意一次排列。

#### 成功与失败如何解释

- 若去重并对顺序边际化后，验证方法仍稳定优于强单来源和随机并列基线，可把结果表述为选择证据；
- 若结果高度依赖顺序，主张必须改为“评分分辨率不足，tie-break 是当前瓶颈”；
- 若 exact 去重后增益显著缩小，应承认原分析受到重复候选结构影响，并用修订结果替换原主结论；即使默认首出现规则下准确率不变，也必须报告随机并列和顺序边际化后的期望准确率，因为“首出现”本身仍编码来源顺序；
- 无论结果方向如何，原始八槽审计记录都应保留，不能覆盖或删除。

#### 预期新增产出

- 主文表：去重和顺序边际化后的选择结果；
- 主文图：随机排列下准确率分布或稳定性区间；
- 补充表：每种选择器的来源比例、rescue/harm 和并列结构；
- 版本化的去重映射与重分析脚本。

### 4.4 实验 E4：Metamorphic-State Critic 的针对性验证

**优先级：P2；建议新增构造状态，部分分析可复用现有代码。**

#### 研究目的

当前构造状态分析没有发现校正后显著差异。后续实验不应仅扩大相似状态数量，而应构造能够区分“在原快照上碰巧得到正确结果”和“SQL 语义真正正确”的诊断性状态。

#### 设计建议

根据真实错误类型设计 mutation operator，例如：增加会破坏错误 join 的孤立记录、加入 NULL、插入重复值、改变排序并列、加入边界时间、改变基数、增加同名资产、调整阈值附近数值。每个 operator 必须说明它针对哪类 SQL 语义错误，以及正确 SQL 应满足的 invariant 或 expected transformation。

选择一批在原数据库上执行结果相同、但语义结构不同的候选对作为主要测试对象。比较 validation-only 与 validation + critic 的错误接受率、正确候选误伤率和额外执行成本。状态及语义预期应由独立审核者确认，不能由设计同一规则的人单独认证。

#### 成功与失败如何解释

- 若 critic 显著降低语义错误接受且误伤可控，可把它定位为风险降低组件；
- 若只在人工挑选案例有效，应明确标注 targeted diagnostic，不得推广到整体准确率；
- 若仍无新增区分力，应弱化 critic 的实证贡献，并保留为架构扩展点。

#### 预期新增产出

- 状态 mutation 目录与适用错误类型表；
- false-accept/false-reject 对照表；
- 成本—风险图及全部状态生成脚本。

### 4.5 实验 E5：统计稳健性与依赖结构重分析

**优先级：P2；现有数据可先完成，新实验结束后应统一复算。**

#### 必做分析

- 明确70个结构簇的生成规则，并报告58个单例簇对检验功效和交换性假设的影响；
- 在题目级配对分析、结构簇分析和 leave-one-template-family-out 分析之间做敏感性比较；
- BIRD 结果同时按题目和数据库层级报告，但承认只有11个数据库时数据库级推断精度有限；
- 对所有主要对比报告绝对效应、区间和校正后的 p 值；
- 将 primary、secondary 和 exploratory families 在方法和表注中预先区分；
- 对随机化或 bootstrap 过程说明随机化单位、重复次数、种子和有限样本修正；
- 非显著结果使用“未观察到足够证据支持差异”，不使用“两个方法相同”。

#### 为什么要做

论文现有统计处理总体谨慎，但依赖簇主要是结构代理且大量为单例。增加多种分析单位的敏感性结果，可以证明结论不依赖某一个方便的簇定义，也能防止审稿人把功效不足与方法无效混为一谈。

#### 预期新增产出

- 统计分析注册表；
- 主要/次要检验族清单；
- 题目级、结构簇级、数据库级敏感性表；
- 可复现的随机化和 bootstrap 脚本。

### 4.6 实验 E6：复现与发布一致性验证

**优先级：P1；不需要新增研究数据，但必须在投稿前完成。**

建立一次全新的 release，而不是在旧清单上局部修补。首先处理三项已确认的不一致：本地 `verify_package.py` 对当前 `paper_applsci.tex` 报哈希不匹配；公开仓库仍是旧 C1--C5/x10 与 GPT/DeepSeek 配置；公开仓库的 CC BY 4.0 声明与本地 data card 的“再分发权限未解决”相冲突。随后冻结论文和数据版本，从干净目录执行全部测试和主表复算，生成新版 PDF 并逐页视觉检查，重新生成文件哈希和 manifest，再从公开 release 下载并复验。最终在补充材料中报告可复现范围：哪些结果可从逐题数据完全复算，哪些因模型权重、第三方数据库或权利限制只能重放而不能重新生成。

成功标准是公开 release 与投稿 PDF 的题目、模型、样本量、主要数字、许可状态和哈希完全一致，`python verify_package.py` 在下载后的干净副本上完整通过，且不存在需要作者口头解释才能发现的旧版本材料。局部单元测试通过不能替代这一门禁。

## 5. 两条可选修订路线

### 路线 A：完整增强路线（推荐）

适用于可以新增模型调用、准备外部电网数据并安排专家审核的情况。

必须完成 E1、E2、E3、E5、E6；E4 至少完成针对性小规模验证。完成后可保留当前多智能体和电网应用定位，但最终措辞必须由新结果决定。该路线最有可能把论文从“有价值但证据不足的工程框架”提升为“方法、应用和复现三方面均完整的应用研究”。

### 路线 B：保守收缩路线

适用于无法及时取得新电网数据、专家审核或模型预算的情况。

至少完成 E3、E5、E6，并全面执行第 3 节的文本收缩。标题使用 multi-role coordination/evaluation，摘要和结论不再声称完整框架提高准确率；GridDB 被明确描述为 synthetic case study；BIRD 被定位为通用数据库可移植性检查；80→101 只作为顺序敏感的历史池描述。该路线仍可能形成一篇审计和复现导向的 Applied Sciences 工程论文，但社区贡献和评分上限会低于路线 A。

不建议采用第三种方案，即保留强标题和结论但只补充少量文字。这不会解决审稿意见中的结构性问题。

## 6. 推荐执行顺序与依赖关系

### 阶段 0：冻结当前版本

保存当前 TeX、PDF、数据和脚本的只读快照，记录哈希。所有新分析写入新版本目录，不覆盖历史证据。建立修订台账，为每项任务分配 ID、负责人、输入、输出和状态。

### 阶段 1：先完成现有数据可支持的重分析

优先完成 E3 和 E5。该阶段不需要新增 LLM 调用，却会决定历史池结果还能否保留为主要证据，也会影响新实验中候选去重和并列规则的设计。

### 阶段 2：确定论文路线并冻结新实验协议

根据 E3 结果和可用资源在路线 A、B 之间作出决定。若采用路线 A，在任何正式模型运行前完成 E1/E2 的数据、对照、预算、指标和统计方案冻结。先进行小规模 dry run 检查流程，不使用正式测试 gold 调参。

### 阶段 3：开展前瞻性实验

依次完成电网数据审核、E1 主实验、E2 跨模式分析和 E4 针对性 critic 诊断。每次运行保留原始输出、stderr、运行环境、耗时、token、模型哈希、随机种子和失败状态。

### 阶段 4：统一统计与证据审计

在所有实验完成后一次性运行冻结的主分析，生成表格和图形。核对正文数字、图表、CSV/JSON 和逐题记录。探索性分析必须单独标注，不得在结果出来后升级为 primary evidence。

### 阶段 5：按证据重写论文

先重写 Methods 和 Results，再重写 Introduction、Discussion、Limitations、Conclusion，最后写摘要和标题。这样可以避免先写强主张、再勉强寻找实验支持。完成后逐条检查本文档第 3 节的验收标准。

### 阶段 6：复现发布与投稿检查

完成 E6，同步公开仓库、release、Data Availability、PDF 和 manifest。最后进行一次“陌生读者测试”：只向检查者提供论文和公开仓库，确认其能回答系统实际调用了哪些角色、主要对照是什么、哪些结果是前瞻性、哪些是回顾性、如何复算主表以及结论不能推广到哪里。

## 9. 最终投稿门禁

只有同时满足以下条件，才建议提交：

- 已明确选择路线 A 或路线 B，标题、摘要和结论与该路线一致；
- 所有 P1 项均已解决，或因无法解决而在全文中完成等比例的主张收缩；
- 新实验采用未见测试数据，正式运行前冻结协议，且主要结果可从逐题记录复算；
- 历史池结果已经完成去重和顺序边际化，不再把任意固定顺序当作因果证据；
- 论文明确区分前瞻性、回顾性和探索性结果；
- 现有 Table 1 已纳入 TEAM、MAC-SQL、QC-MaSQL、R3 等最接近的方法，并解释本工作的真实差异；
- 公开仓库已从旧 C1--C5/x10 配置升级到与投稿稿一致的 Qwen/Granite、五角色、BIRD、构造状态和历史池版本；
- GridDB 的再分发权利已由权利主体确认，论文、data card、仓库和许可证表述一致；
- TeX 无 TODO 或占位字段，通讯邮箱和全部声明已经作者确认，并由最新版 LaTeX 重新生成 PDF；
- 在公开 release 的干净副本中执行 `python verify_package.py` 完整通过，图形、参考文献、交叉引用、哈希、单元测试和逐页视觉 QA 均无错误；
- 最终全文不存在超出实验边界的“robust”“generalizable”“multi-agent improvement”表述。

完成上述工作后，论文最有说服力的定位应是：MA-SQLGrid 不只是把多个模块串联起来，而是提供了一个能够区分候选生成、执行安全、语义证据、选择风险和审计责任的可复现协议；若前瞻性实验进一步证明其在相同预算下带来稳定收益，则可以在此基础上主张完整架构的实证价值。
